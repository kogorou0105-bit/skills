# 用开发故事理解技术架构

把项目从最小可用版本到逐步完善的过程，写成连续、具体、容易理解的开发故事。

## 参考资料

- 用户要求结合技术分类、但没有提供分类时，读取 [技术分类地图](references/technical-categories.md)。用户提供的分类优先；这些分类是查找问题的地图，不是岗位划分、完整课程或必经步骤。
- 首次撰写完整故事，或需要校准叙事风格时，读取 [商家订单与结算平台示例](references/merchant-platform-story.md)。借鉴因果推进和解释深度，不照搬业务、事件或技术选型。

## 写作方式

- 沿用用户的项目、技术栈和分类；缺少的信息用适度假设补齐，并说明这是教学场景。
- 从真实使用者的需求和最小业务闭环开始，不先列技术栈。
- 用需求变化、数据更新、任务失败、多人使用或负载变化推进情节。
- 每个关键情节讲清：具体问题 → 发生原因 → 对应技术分类 → 可行方案 → 代价、边界或后续问题。不必机械写成五个小标题。
- 对重要方案补一句验证办法，让读者知道如何判断问题是否解决。区分使用某个组件与读懂其源码。

## 判断原则

- 优先采用当前规模下简单可行的方案；不要默认引入微服务、消息队列、缓存或分布式锁。
- 区分问题类别、具体工具和领域能力；例如权限控制是问题类别，Casbin 是可选工具，文档检索是知识库的领域能力。
- 权限与数据正确性从开始设计；通过设计时发现的风险解释，不必虚构事故后才补救。
- 只覆盖项目真正需要的分类，不为凑齐目录制造需求。新增需求可能暴露更早的设计不足，改动不保证只有收益。
- 不把假设情节写成用户实际经历，不编造效果数字、生产验证或工具能力。涉及具体工具的版本与支持范围时，查官方资料再下结论。

## 输出

写成可独立阅读的文章，以自然段和连续情节为主。按需加入少量代码、流程或对照表，避免变成术语清单。让读者理解为什么使用、什么时候暂时不用，以及仍需处理什么。篇幅、技术深度和发布格式遵循用户要求；本技能本身不要求部署或对外发布。
