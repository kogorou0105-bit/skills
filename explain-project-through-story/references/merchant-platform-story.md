# 示例：商家订单与结算平台怎样逐步长出来

这是一篇教学故事，用来示范需求、问题和技术分类如何相互连接。本次覆盖后端全部 12 类。情节不代表真实公司经历，编号是技术地图索引，不是架构成熟度。实际项目不必全部引入这些组件。

## 先让商家发布商品

假设你加入一家互联网公司，负责开发商家订单与结算平台。第一项需求很简单：商家填写商品名称、价格和库存，点击发布，用户就能查看商品。

你先提供创建和查询商品的接口。但每个接口都要解析参数、校验格式、返回错误，于是使用 Go 服务框架组织路由与中间件，把业务逻辑和请求处理分开。这对应 **① 服务框架与 API**。

商品不能随着进程重启而消失，于是你设计商品、订单等数据表，保存在 PostgreSQL。这对应 **② 数据库与存储**。第一条链路建立起来：接收请求、执行业务、保存数据、返回结果。你用接口测试和重启后的数据检查验证闭环。

## 商家不能修改别人的商品

设计编辑接口时，你发现仅凭商品 ID 就允许修改会造成越权。你从开始便加入登录，并检查当前用户是否属于该商家、是否具有编辑权限。这对应 **⑨ 身份认证与权限**。

小王是 A 店铺的员工，即使将请求中的商品 ID 改成 B 店铺的商品，后端也应拒绝。你同时测试允许和拒绝场景，而不只验证页面有没有隐藏按钮。权限库可以帮助判断规则，业务服务仍须正确执行检查。

## 数据访问开始散落，旧系统又需要接进来

接口变多后，同样的查询重复出现，表结构修改也越来越难维护。你整理 Repository 层，用迁移管理数据库变更。公司又要求同步老系统的商家资料，你需要处理外部 ID、新增、更新、重复和同步进度。这对应 **③ 数据访问与同步**。

数据库负责存储和查询；这一层负责业务怎样使用数据，以及变化怎样在系统间传播。重复执行同一批同步后，结果应该保持一致，这是一个可以实际验收的要求。

## 热门商品让数据库变忙

活动开始，同一个商品页面被反复访问。你先检查慢查询、索引和负载，确认瓶颈中确实有大量重复读取，再缓存变化不频繁的商品介绍。这对应 **④ 缓存与性能**。

你必须决定修改后的失效方式，并比较命中率与延迟。商品介绍可以接受有限的更新延迟，库存扣减却需要更严格的正确性，两者不能照搬同一方案。

## 下单接口承担了太多后续工作

最初，创建订单后还要发通知、更新统计、通知仓库。通知服务变慢，竟然拖慢了下单。你重新划分同步承诺与后续处理：保证核心下单规则成立后，可靠地产生事件，让其他模块分别处理。这对应 **⑤ 消息与事件系统**。

消息系统带来了解耦，也带来重复消费与交付失败问题。你需要处理“数据库已提交，但事件尚未发出”，并验证重复消费不会重复产生业务效果。小规模阶段也可以先使用数据库事件表，不必立即部署独立消息中间件。

## 有些事情要等时间，有些要走步骤

产品提出：订单超过十五分钟未付款应关闭；退款需要申请、审核、执行。你设计延迟检查与状态流转，这对应 **⑥ 任务调度与工作流**。

关闭订单与支付成功可能同时发生，因此执行任务时仍须重新检查业务状态，而不能认为“定时器响了就一定可以关闭”。消息关注发生了什么，工作流关注何时执行、推进到哪一步、失败后怎样恢复。

## 多个实例重复生成结算单

后台部署多个实例后，它们可能同时领取每日结算任务。你引入任务领取、租约、选举或适用的锁机制，这对应 **⑦ 分布式协调**。

锁过期或进程暂停仍可能导致重复执行，因此你还为结算设置业务唯一约束和幂等检查。协调减少重复工作，业务约束保证重复发生时仍然正确。可以通过重复投递和中断执行测试这条规则。

## 请求需要统一进入，也需要控制流量

服务增多后，客户端不应记住每个服务地址。活动流量还要求限流与超时，避免下游持续失败时请求无限堆积。你按规模引入统一入口和流量控制，这对应 **⑧ 网关与流量治理**。

入口管理不替代业务授权，也不是拆成多个服务的理由。团队规模小时，单体应用加反向代理可能已经足够。通过限流测试和依赖超时场景验证行为，而不只确认配置文件能加载。

## 商家希望立即收到新订单

商家不想不断刷新网页，也希望实时看到批量导出进度。你按交互需要选择 SSE、WebSocket 或轮询，并设计重连与补取机制。这对应 **⑩ 实时通信与协作**。

实时连接也要遵守店铺权限。断线不应导致永久漏单，可以通过恢复连接后重新查询可靠状态来补齐。没有持续更新需求的页面不必使用长连接。

## 下单偶尔很慢，但你在本机复现不了

你开始记录日志、指标与调用链，区分受影响范围和耗时阶段，这对应 **⑪ 观测与运行诊断**。一次慢请求可能卡在数据库、库存或其他依赖，不能只根据最终响应时间猜原因。

你还要控制观测成本和敏感内容。制造一次受控的依赖延迟，检查是否能在记录中定位，可以验证这套诊断能力是否实际可用。

## 最后，把订单和资金事实连接起来

商家开始查询收入、退款与结算。你意识到订单状态和资金账本不是同一件事：需要关联交易、手续费、退款与支付渠道结果，并处理对账差异。账本的原子记账、幂等与历史追溯，是这个领域自己的核心问题。

当接口、存储、权限、同步、任务、消息和结算围绕业务规则共同运作时，我们研究的就是 **⑫ 完整业务系统**。它不是另一个组件，而是组合后的整体。

这个故事的阅读方法是：每出现一个方案，都追问它解决了哪个具体问题、为什么现在需要、增加了什么复杂度，以及如何验证。换成知识库项目，主角会变成文档、索引和团队，叙事方法可以复用，架构选择仍需重新判断。

## 分类覆盖检查

下表中的阶段与采用状态属于假设故事，不代表某个真实产品已采用对应设计。

| 既定分类 | 对应情节 | 故事中的采用判断 |
| --- | --- | --- |
| 01 服务框架与 API | 发布商品时组织接口与校验 | 起步采用。 |
| 02 数据库与存储 | 商品与订单需要持久化 | 起步采用。 |
| 03 数据访问与同步 | 整理查询与迁移，同步旧系统 | 随数据访问复杂度和集成需求推进。 |
| 04 缓存与性能 | 热门商品重复读取 | 测量瓶颈后采用，先处理查询与索引。 |
| 05 消息与事件系统 | 下单后的通知和统计拖慢响应 | 先明确异步边界，按需要选择事件表或消息系统。 |
| 06 任务调度与工作流 | 超时关单和退款审核 | 出现定时与多步骤需求时采用。 |
| 07 分布式协调 | 多实例重复执行结算 | 多实例阶段考虑，仍保留业务幂等约束。 |
| 08 网关与流量治理 | 统一入口与活动流量管理 | 按规模采用；早期反向代理与应用限流可能足够。 |
| 09 身份认证与权限 | 防止跨店铺修改商品 | 从开始设计，接口与数据访问共同执行。 |
| 10 实时通信与协作 | 新订单提醒和导出进度 | 先按及时性要求选择轮询、SSE 或 WebSocket。 |
| 11 观测与运行诊断 | 下单偶发缓慢 | 保留基础观测，随诊断需求完善。 |
| 12 完整业务系统 | 订单、库存、资金与对账关联 | 随业务闭环逐步形成。 |
