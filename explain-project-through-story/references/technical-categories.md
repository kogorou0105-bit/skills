# 技术分类地图

本地图沿用用户已有的开源项目调研表分类，是故事的必需覆盖清单。它不是严格互斥的分类体系，也不是强制学习或采用顺序。编号用于稳定引用，不要求按编号安排情节。

按 SKILL.md 确定领域范围后，必须保留该领域全部原始分类；仅当用户明确修改分类时采用用户版本。一个问题可涉及多个类别，须分别说明对应关系。工具名只是可选实例，不代表默认选型。补充分类不能替代既定分类。

## 后端：按工程问题分类

| 分类 | 主要解决的问题 |
| --- | --- |
| 01 服务框架与 API | 接收请求、校验输入、组织业务逻辑、返回结果，统一接口约定。 |
| 02 数据库与存储 | 数据保存、查询、持久化和存储结构；包括业务数据、文件与专项索引。 |
| 03 数据访问与同步 | 数据访问层、查询封装、数据库迁移、外部数据同步与变更传播。 |
| 04 缓存与性能 | 降低延迟、减少重复计算和资源消耗；从测量和瓶颈定位开始。 |
| 05 消息与事件系统 | 传播事件、解耦生产与消费；考虑交付可靠性、顺序及重复消费。 |
| 06 任务调度与工作流 | 定时或延迟执行、后台任务、步骤编排、状态推进和失败恢复。 |
| 07 分布式协调 | 多实例任务归属、租约、选举和共享执行规则；不能只靠锁保证业务正确。 |
| 08 网关与流量治理 | 请求入口、路由、限流、超时和流量管理；不替代业务层授权。 |
| 09 身份认证与权限 | 确认身份、允许的操作与数据范围，处理租户隔离和访问控制。 |
| 10 实时通信与协作 | 持续推送、双向交互、协同状态、断线重连和取消。 |
| 11 观测与运行诊断 | 日志、指标、调用链、性能分析和故障定位。 |
| 12 完整业务系统 | 前述能力围绕领域规则组合；属于综合样本，不是另一个基础组件。 |

容易混淆的边界：

- 消息关注“发生了什么、通知谁”；工作流关注“何时执行、步骤与状态”。同一方案可能兼具两者。
- 数据库负责保存和查询；数据访问与同步关注业务如何使用数据，以及变化怎样跨系统传播。
- 缓存、锁、重试都不是独立的正确性保证，需要与约束、版本、幂等和失效规则配合。

## 前端：按应用能力与开发环节分类

| 分类 | 主要解决的问题 |
| --- | --- |
| 01 框架运行时与编译 | 组件、渲染、更新和模板／组件代码转换。 |
| 02 路由与应用框架 | 页面导航、布局、加载与应用级组织。 |
| 03 状态管理与响应式 | 共享状态、派生数据、更新传播和状态一致性。 |
| 04 服务端数据与表单 | 请求、加载与错误状态、服务端数据缓存、输入校验和提交。 |
| 05 组件系统与可访问性 | 可复用交互组件、键盘操作、语义和辅助技术支持。 |
| 06 布局动画与交互 | 布局适配、动画、拖拽、手势与操作反馈。 |
| 07 编辑器与文档模型 | 富文本、文档结构、选区、编辑操作和撤销重做。 |
| 08 图表图形与流程画布 | 数据可视化、图形渲染和节点连线交互。 |
| 09 本地数据与协同 | 本地持久化、同步、冲突处理和多人协作。 |
| 10 构建编译与工程组织 | 打包、依赖、构建缓存、代码转换和多包组织。 |
| 11 测试质量与调试 | 单元／交互／端到端测试、定位错误和质量检查。 |
| 12 跨端与离线体验 | 不同终端、离线使用和恢复连接后的行为。 |
| 13 完整产品与应用架构 | 页面、状态、数据、权限与交互怎样组织成产品。 |
| 14 文档与内容系统 | 内容组织、发布、文档站和内容驱动页面。 |

## Agent：混合能力、场景与研究环节

| 分类 | 主要解决的问题 |
| --- | --- |
| 01 开发框架与编排 | 模型、工具、状态、运行循环与任务流程的组织。 |
| 02 编程与终端 Agent | 在代码仓库和终端中执行开发任务。 |
| 03 成品应用与平台 | 将 Agent 能力组织为用户可用的产品与管理平台。 |
| 04 浏览器与桌面 Agent | 通过界面观察和操作完成任务。 |
| 05 语音与实时 Agent | 音频流、低延迟交互、打断与会话协调。 |
| 06 工具协议与连接器 | 发现和调用外部能力、连接数据与应用。 |
| 07 记忆与上下文 | 保存、选择、压缩和更新任务相关信息。 |
| 08 沙箱与执行基础设施 | 为代码与工具执行提供环境、资源边界和隔离。 |
| 09 观测评测与优化 | 记录执行过程、评估结果并定位效果与成本问题。 |
| 10 基准与研究环境 | 提供可重复任务、环境与比较方法。 |
| 11 训练与算法研究 | 改进模型或策略本身的训练与算法。 |

Agent 表不是单一维度：编程 Agent 是应用场景，记忆是能力模块，评测是开发环节。不要把它们写成依次升级的阶段。固定检索后生成可以称为 RAG 工作流，无需为了归类强称 Agent。

## 将地图用于故事

先将所选领域的每个分类对应到具体业务问题，再以自然的因果顺序写故事。正文标注原始编号与名称，解释方案、代价与验证办法。当前不需要的能力也须说明何时可能需要及为何暂不采用；确实不适用则说明原因。

文末逐项列出覆盖表，核对后端 12 类、前端 14 类或 Agent 11 类是否全部出现；跨领域时分别核对，不把同名或近似类别自动合并丢失。用户只关注一个领域时，不必展开其他领域。

领域能力可单列为“补充分类”，例如知识库的解析／检索、账本的平衡记账。固定工作流不是自主 Agent，工程评测也不等于模型训练；无法适用的分类要如实说明，不能为了覆盖编造功能。
